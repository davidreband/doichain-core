# Стратегия обновления Doichain Core на Namecoin Core (и на все следующие версии)

Дополняет `DOICHAIN_FORK_INVENTORY.md` (инвентаризация изменений). Дата: 2026-08-07.

---

## 0. Исходная позиция

Хорошая новость: перенос на namecoin 29.x **уже сделан и почти полон**. Ветка
`doichain-nc29-migration` стоит на `upstream/29.x` @ `d00111caac` и несёт 47 своих коммитов.
Из старого Doichain функционально не потеряно ничего, кроме одного 8-строчного фрагмента
(`core_write.cpp`, см. инвентаризацию §4.1).

Но целевая версия уже устарела. Актуальное состояние upstream на 2026-08-07:

| Релиз namecoin | Дата | Bitcoin Core в основе |
|---|---|---|
| nc29.0 | 2025-04 | 29.0 |
| nc29.1 | 2025-09-08 | 29.1 — **последний коммит ветки 29.x, линия закрыта** |
| nc30.0 / 30.1 / 30.2 | 2025-10-13 / 2025-12-22 / 2026-01-12 | 30.x |
| nc31.0 | 2026-04-20 | 31.0 |
| **nc31.1** | **2026-07-13** | **31.1 — актуальный стабильный** |
| `upstream/master` | 31.99, синхр. с bitcoin master на 2026-08-03 | разработка 32 |

Расстояние от текущей ветки: до `nc29.1` — 49 коммитов, до `nc30.2` — 2205, до **`nc31.1` — 4325**.

**Целевая версия миграции — `nc31.1`, а не nc29.** Обоснование в §1.0.

Плохая новость: перенос сделан так, что **следующее** обновление (nc30) будет стоить столько же,
сколько это. Причины:

1. 47 коммитов не разделены по смыслу: «Bug fix», «disabled checks», «qt fixes», «Todo: nameop» —
   при ребейзе невозможно понять, что можно дропнуть, а что нельзя.
2. Массовое переименование идентификаторов (`IsNamecoin`→`IsDoichain` и др.) даёт ~40 конфликтов
   в файлах, которые upstream активно меняет, и не даёт ничего взамен.
3. Отступления от консенсуса оформлены как закомментированный код — при ребейзе они
   молча «чинятся» обратно и цепь перестаёт синхронизироваться.
4. Нет ни одного теста на `name_doi` — то есть нет способа доказать, что после ребейза
   ничего не сломалось.

Стратегия ниже решает именно это: не «как перенести ещё раз», а **как сделать так, чтобы
переносить больше не приходилось**.

## 1.0 Почему цель — nc31.1, а не nc29.x

Расстояние в 4325 коммитов выглядит пугающе, но для форка Doichain оно почти не имеет
значения. Замеры по upstream между `nc29.0` и `nc31.1`:

| Файл, который правит Doichain | Изменения в upstream 29 → 31 |
|---|---|
| `src/script/names.h`, `src/script/names.cpp` | **0 строк** — файлы не менялись |
| `src/names/mempool.h`, `src/names/mempool.cpp` | **0 строк** |
| `src/names/main.cpp` | 13 строк (`unsigned flags` → `script_verify_flags`) |
| `src/names/main.h` | 5 строк |
| `src/rpc/names.cpp` | 27 строк |
| `src/wallet/rpc/walletnames.cpp` | 36 строк |
| `src/txdb.cpp` | 93 строки |
| `src/kernel/chainparams.cpp` | 235 строк |

То есть **name-слой namecoin практически заморожен** — а именно в нём живёт вся ценность
форка Doichain (слои C, D, F инвентаризации). Они перенесутся на 31.x почти без конфликтов.

Основной объём конфликтов даст совсем другое: `validation.cpp` (+1091/−1235), `txmempool.cpp`,
`init.cpp`, `node/miner.cpp`, `wallet/spend.cpp` — файлы, в которых Doichain меняет **только**
`IsNamecoin()` → `IsDoichain()`. Это эмпирическое подтверждение рекомендации §2.1: откат
косметических переименований снимает большую часть стоимости перехода 29 → 31.

Одно предупреждение по месту: в 31.x функция `NameOpToUniv` переехала
`core_write.cpp` → `core_io.cpp`. Фикс блокера §4.1 инвентаризации после ребейза окажется
в другом файле.

Аргументы за то, чтобы целиться сразу в 31.1:

* ветка `29.x` у namecoin **закрыта** (последний коммит 2025-09-08), обновлений безопасности не будет;
* вся работа фаз 0–3 одинакова независимо от базы — делать её дважды нет смысла;
* шаг в name-слое, ради которого форк существует, близок к нулю;
* Doichain и так пропустил 9 мажорных версий; закрепиться на уже неподдерживаемой — повторить ту же ошибку.

Порядок при этом важен: **нарезка коммитов, откат переименований и формализация консенсуса
делаются ДО ребейза, на базе 29.x.** Причина: ребейз 47 грязных коммитов через 4325 upstream-коммитов
неуправляем, а закомментированные проверки консенсуса (E1–E7) при таком ребейзе просто
восстановятся в upstream-виде и молча сломают синхронизацию цепи. См. изменённый план в §4.

## 1. Базовый принцип: Doichain = upstream + управляемая очередь патчей

Модель, которую применяет сам Namecoin поверх Bitcoin, и которую стоит применить здесь:

```
upstream/29.x  (namecoin, не трогаем никогда)
      │
      └── doichain/29.x    = upstream/29.x + N тематических коммитов
                              где N ≈ 10–12, каждый с осмысленным заголовком
```

Обновление на nc30 = `git rebase --onto upstream/30.x upstream/29.x doichain/29.x`.
При хорошо нарезанных коммитах это 1–2 дня работы, а не 3 месяца.

**Правила ветки Doichain:**

* Никаких мёрдж-коммитов из upstream в свою ветку. Только rebase.
* Один коммит = одна тема. Заголовок описывает **что** и **почему**.
* Отладочные коммиты («added logging», «Bug fix», «Todo») в ветке не живут — они
  сквошатся в тематический коммит, к которому относятся.
* Ветка всегда собирается и проходит тесты на каждом коммите (иначе `git bisect` бесполезен).

**Целевая нарезка коммитов** (вместо нынешних 47):

| # | Коммит | Содержание |
|---|---|---|
| 1 | `chainparams: Doichain networks` | genesis, порты, magic, seeds, base58/bech32, форк-высоты, пустая `mapHistoricBugs` |
| 2 | `consensus: Doichain consensus divergences` | E1–E7 из инвентаризации, **явным кодом с флагами в `Consensus::Params`**, не комментариями |
| 3 | `script: add OP_NAME_DOI` | `script.h`, `script/names.{h,cpp}` |
| 4 | `names: DOI registration/update rules` | `names/main.cpp` — ветка `OP_NAME_DOI` в `CheckNameTransaction` |
| 5 | `names: track DOI ops in mempool` | `names/mempool.{h,cpp}`, `kernel/mempool_entry.h` |
| 6 | `txdb/validation: allow duplicate DOI names in UTXO set` | `txdb.cpp`, `validation.cpp` |
| 7 | `rpc: name_doi and DOI in tx decoding` | `rpc/names.cpp`, `rpc/client.cpp`, **`core_write.cpp`** |
| 8 | `wallet: name_doi RPC` | `wallet/rpc/walletnames.cpp`, `wallet/rpc/wallet.cpp`, `wallet/receive.cpp` |
| 9 | `test: functional and unit tests for name_doi` | новые файлы, конфликтов с upstream не даёт |
| 10 | `build: Doichain product names and version` | CMake, `clientversion` |
| 11 | `qt: Doichain branding` | логотип, единицы, строки |
| 12 | `doc: Doichain documentation` | README, man, эти два документа |

Коммиты 3–9 — это **ценность форка**. Коммиты 10–12 — брендинг, который при конфликте
всегда решается в пользу Doichain без раздумий. Разделение этих двух групп само по себе
сильно ускоряет ребейз.

## 2. Сократить поверхность конфликта

### 2.1 Откатить косметические переименования в коде

`IsNamecoin()` → `IsDoichain()`, `SetNamecoin()` → `SetDoichain()`, `NAMECOIN_VERSION` →
`DOICHAIN_VERSION` (значение то же `0x7100`), `TxAllowedForNamecoin` → `TxAllowedForDoichain`,
переименования в комментариях.

Это ~40 правок в файлах, которые upstream меняет постоянно: `validation.cpp`, `policy.cpp`,
`wallet.cpp`, `primitives/transaction.h`, `node/miner.cpp`. Каждое обновление — конфликт
в каждой из этих точек, и каждый раз человек должен вручную решать один и тот же тривиальный
вопрос.

**Рекомендация:** оставить upstream-имена в C++-коде, а брендинг держать только там, где
его видит пользователь: строки UI, RPC-справка, имена бинарников, документация, `CLIENT_NAME`.
Если имя `IsNamecoin()` в коде Doichain режет глаз — сделать один алиас в заголовке:

```cpp
// В Doichain это те же самые транзакции; имя сохранено от upstream,
// чтобы не порождать конфликты при обновлениях.
bool IsNamecoin() const { return version == NAMECOIN_VERSION; }
```

Это решение стоит принять **сейчас**, до нарезки коммитов, — потом откатывать дороже.
Экономия: примерно 60–70 % конфликтов при каждом будущем обновлении.

### 2.2 Вынести DOI-логику в отдельные файлы

Сейчас ветка `OP_NAME_DOI` живёт внутри `CheckNameTransaction()` — 80 строк в самой
конфликтной функции форка. Вместо этого:

```
src/names/doi.h     // правила DOI: CheckDoiTransaction(), IsDoiNameAllowed(), константы
src/names/doi.cpp
```

а в `names/main.cpp` остаётся один хук:

```cpp
if (nameOpOut.getNameOp() == OP_NAME_DOI)
    return CheckDoiTransaction(tx, nHeight, view, nameOpIn, nameOpOut, nameIn, state);
```

Тот же приём — для мемпула. Правило: **в файлах upstream должны оставаться только вызовы,
вся логика — в своих файлах.** Свои файлы конфликтов не дают никогда.

### 2.3 Формализовать отступления от консенсуса

Пункты E1–E7 инвентаризации сейчас — закомментированные строки. При ребейзе
`git rebase` восстановит upstream-версию и цепь Doichain перестанет валидироваться,
причём молча и не сразу (только на конкретном историческом блоке).

Правильная форма — поля в `Consensus::Params`, задаваемые в chainparams:

```cpp
// kernel/chainparams.h
struct Params {
    ...
    /** Doichain: PoW difficulty bits are not enforced (историческая цепь содержит
     *  блоки с nBits, не совпадающими с retarget-расчётом namecoin). */
    bool fSkipPowBitsCheck = false;
    /** Doichain: NAME_FIRSTUPDATE не требует входа NAME_NEW. */
    bool fRequireNameNewInput = true;
    /** Doichain: высота, после которой запрещена перезапись существующего DOI. */
    int nDoiOverwriteForbiddenHeight = std::numeric_limits<int>::max();
};
```

```cpp
// validation.cpp
if (!consensusParams.fSkipPowBitsCheck &&
    block.nBits != GetNextWorkRequired(pindexPrev, &block, consensusParams))
    return state.Invalid(...);
```

Выгода тройная: (1) правило видно в коде и не исчезает при ребейзе; (2) для regtest можно
включить строгую проверку и тестировать её; (3) в chainparams появляется единственное место,
где записаны все отличия консенсуса Doichain — это и есть недостающая спецификация форка.

**Обязательно** к каждому такому флагу — комментарий с ответом на вопрос «какой блок сломается,
если это включить». Для E4 такой блок уже известен и записан в TODO:
`height=29966`, `1173d2615de4aba9785646bc414040e622cc04869593f006872b9013e1b1201b`.
Для остальных его нужно найти (см. фазу 2).

## 3. Тесты как условие безопасности ребейза

Без них любая из перечисленных перестроек — рулетка. Минимальный набор:

**Functional (`test/functional/name_doi.py`, по образцу `name_*.py` из namecoin):**
1. `name_doi` регистрирует новое имя; появляется в `name_show`/`name_scan`.
2. `name_doi` на том же имени со своим входом = обновление.
3. `name_doi` без входа на существующем имени: разрешено до высоты N, отклонено после.
4. `name_doi` с именем `d/foo` отклоняется мемпулом.
5. Два `name_doi` на одно имя в мемпуле (chain limit = 2).
6. Реорг с блоком, содержащим `name_doi` — БД имён консистентна.
7. `decoderawtransaction` / `getrawtransaction verbose` над `name_doi` **не роняет узел**
   (тест на баг §4.1 инвентаризации).
8. `-checknamedb=1` после серии DOI-операций проходит.

**Unit (`src/test/name_doi_tests.cpp`):** парсинг/сборка скрипта `buildNameDOI`, инварианты
`CNameScript` для `OP_NAME_DOI`, поведение `getNameOp()` на мусорных скриптах.

**Интеграционный тест уровня сети (важнее всех остальных):** полная синхронизация mainnet
с нуля до текущей высоты + `-checknamedb=1` + `-reindex`. Это единственная настоящая проверка
того, что консенсус не разъехался. Прогонять на каждом обновлении upstream, до релиза.
Зафиксировать эталон: высота, `getblockchaininfo`, хеш тип-блока, `gettxoutsetinfo` — и сверять.

## 4. План работ по фазам

### Фаза 0 — стабилизировать то, что есть (1–2 дня)

Цель: рабочий узел на текущей ветке, без перестроек.

1. Вернуть `OP_NAME_DOI` в `core_write.cpp` (§4.1 инвентаризации) — **блокер**.
2. Убрать `LogPrintf`-отладку из `CheckNameTransaction` (или `LogDebug(BCLog::NAMES, …)`).
3. Убрать `#define error(...)`, дописать оставшиеся места на `LogError`.
4. Убрать `#include` из середины `names/main.cpp`, мёртвую ветку `"doi: "` в `wallet/receive.cpp`.
5. Собрать, прогнать `ctest` и `test_runner.py`.
6. Пометить `MIGRATION_PLAN.md` как устаревший (в нём выдуманные RPC-команды) или удалить.

**Критерий готовности:** `doichaind` синхронизирует mainnet, `name_doi` создаётся,
`getrawtransaction verbose` над ней не падает.

### Фаза 1 — навести порядок в консенсусе (3–5 дней)

1. Перевести E1–E7 в флаги `Consensus::Params` (§2.3).
2. Для каждого флага найти и записать блок-обоснование. Метод: включить проверку,
   запустить `-reindex` на реальной цепи, дождаться первой ошибки, записать высоту и хеш.
   Это даёт **точный** список исторических исключений и, возможно, позволит заменить
   глобальное отключение проверки на список исключений по высоте (как `mapHistoricBugs`
   в namecoin) — то есть вернуть строгую валидацию для всей остальной цепи.
3. Отдельно решить судьбу E1 (проверка `nBits`): если она отключена глобально, любой
   майнер может отправить блок с произвольной сложностью. Это следует либо ограничить
   диапазоном высот, либо задокументировать как принятый риск сети.
4. Вернуть `nMinimumChainWork` к реальному значению (закомментированное
   `…dd46e3b7b9e0ce86713c` на [chainparams.cpp:146](src/kernel/chainparams.cpp#L146)) — после
   того, как синхронизация подтвердится.

**Критерий готовности:** ни одной закомментированной проверки консенсуса в коде;
все отличия — в `Consensus::Params` с комментарием-обоснованием.

### Фаза 2 — тесты (3–5 дней)

Реализовать набор из §3. Писать **до** рефакторинга слоёв, чтобы рефакторинг проверялся ими.

**Критерий готовности:** `test_runner.py name_doi` зелёный; полная синхронизация mainnet
с `-checknamedb=1` проходит; эталонные значения зафиксированы в репозитории.

### Фаза 3 — изоляция и перенарезка (5–7 дней)

1. Вынести DOI-логику в `src/names/doi.{h,cpp}` (§2.2).
2. Принять решение по §2.1 (откат переименований идентификаторов) и выполнить его.
3. Перенарезать историю ветки в 10–12 тематических коммитов (таблица §1) через
   интерактивный ребейз поверх `upstream/29.x`.
4. Переименовать ветки по-человечески: `doichain/29.x` вместо `doichain-nc29-migration`;
   удалить или переименовать вводящую в заблуждение `upstream-29.x` (это копия старого master).
5. Старый `master` тегировать как `doichain-0.20-legacy` и заморозить.

**Критерий готовности:** `git log upstream/29.x..doichain/29.x` читается как оглавление
форка; каждый коммит собирается и проходит тесты.

### Фаза 4 — ребейз на актуальный namecoin nc31.1 (3–5 дней)

Выполняется только после фаз 0–3: коммиты нарезаны, консенсус формализован, тесты есть.

```bash
git fetch upstream --tags
git checkout -b doichain/31.x doichain/29.x
git rebase --onto nc31.1 upstream/29.x doichain/31.x
```

Что ожидать по каждому коммиту из таблицы §1:

| Коммит | Прогноз |
|---|---|
| 1 `chainparams` | Конфликт гарантирован (235 строк churn), но правки механические |
| 2 `consensus divergences` | Конфликт в `validation.cpp`; здесь и окупается формализация через `Consensus::Params` |
| 3 `OP_NAME_DOI` | **Чисто** — `script/names.*` в upstream не менялись |
| 4 `names: DOI rules` | Почти чисто; поправить сигнатуру на `script_verify_flags` |
| 5 `mempool DOI` | **Чисто** — `names/mempool.*` не менялись |
| 6 `txdb/validation` | Небольшой конфликт (93 строки churn в `txdb.cpp`) |
| 7 `rpc + core_write` | `NameOpToUniv` переехал в `core_io.cpp` — перенести правку туда |
| 8 `wallet` | Небольшой конфликт (36 строк) |
| 9 `tests` | Чисто (свои файлы) |
| 10–12 `build/qt/doc` | Конфликты частые, но решаются в пользу Doichain без раздумий |

После ребейза — **обязательно** полная пересинхронизация mainnet с нуля,
`-checknamedb=1`, `-reindex` и сверка с эталоном из фазы 2. Regtest-тесты расхождение
консенсуса на исторической цепи не поймают.

**Критерий готовности:** `doichaind` на базе nc31.1 синхронизирует mainnet до той же высоты
с теми же значениями `gettxoutsetinfo`, что и узел из фазы 0.

### Фаза 5 — регламент обновлений (постоянно)

```bash
git fetch upstream --tags
git rebase --onto nc32.0 nc31.1 doichain/31.x   # → doichain/32.x
# конфликты ожидаются в chainparams, брендинге и 5-6 hook-точках
cmake -B build && cmake --build build -j
ctest --test-dir build && ./build/test/functional/test_runner.py
# полная пересинхронизация mainnet + -checknamedb=1 + сверка с эталоном
```

Правило: обновляться на каждый мажорный релиз namecoin, **не пропуская версии**. Пропуск
девяти релизов — это и есть причина, по которой нынешняя миграция заняла столько времени.
Один релиз за раз при 10–12 чистых коммитах — предсказуемая работа на несколько дней.

## 5. Что именно защищает от потери изменений

| Механизм | Что защищает |
|---|---|
| `DOICHAIN_FORK_INVENTORY.md` | Полный список изменений с указанием файлов и статуса. Проверяется после каждого ребейза |
| `patches/` (120 патчей) + ветка `master` | Первоисточник старого Doichain. **Не удалять.** Тегировать как `doichain-0.20-legacy` |
| Тематические коммиты (§1) | Изменения видны в `git log`, а не растворены в 47 «Bug fix» |
| Флаги в `Consensus::Params` (§2.3) | Отступления от консенсуса не исчезают при ребейзе |
| Свои файлы `names/doi.*` (§2.2) | Логика DOI физически не может быть затёрта мёрджем upstream |
| Тесты (§3) | Единственный способ **доказать**, что после обновления ничего не потерялось |
| Эталон синхронизации mainnet | Ловит расхождение консенсуса, которое тесты на regtest не увидят |

## 6. Приоритеты, если времени мало

1. **`core_write.cpp`** — узел падает на штатной RPC-операции. Полчаса работы.
2. **Отладочные `LogPrintf` в валидации** — деградация производительности на каждом блоке.
3. **Формализация E1–E7** — иначе следующий ребейз тихо сломает синхронизацию.
4. **Тесты name_doi** — без них всё остальное делается вслепую.
5. Всё остальное (нарезка коммитов, откат переименований, изоляция файлов) — экономия
   времени в будущем, не блокер сегодня. Но именно оно определяет, будет ли переход
   на nc31.1 стоить неделю или ещё один квартал.
